4.3 分层退化坏味道（反模式）

反模式 1：胖 Controller（Fat Controller）

routes_ext.py 4744 行承载 110 个路由，大量路由超过 100 行，最复杂路由（admin_restore_webdav_backup）超过 200 行。业务逻辑直接内联于路由函数，无 Service 层抽象。

反模式 2：SQL 外露（绕过 ORM 直接操作 sqlite3）

# webhook_utils.py:115 — 直接 sqlite3 写日志，绕过 SQLAlchemy
conn = sqlite3.connect(_resolve_db_file(), timeout=10)
c = conn.cursor()
c.execute("INSERT INTO webhook_logs ...")

# app.py:662-673 — 迁移时直接 sqlite3 修复孤儿索引
_fix_conn.execute("PRAGMA writable_schema=1")
_orphan_indexes = _fix_conn.execute("SELECT name FROM sqlite_master WHERE ...")

3 处独立 sqlite3.connect() 绕过 ORM，在多 Worker 下可能产生连接竞争；_resolve_db_file() 硬编码路径探测逻辑与 app.py 中的路径逻辑重复。

反模式 3：全局可变状态（多 Worker 不安全）

# app.py:1062-1065 — 模块级内存字典，多 Worker 下不共享
LOGIN_FAIL_COUNTS = {}
LOGIN_LOCK_UNTILS = {}
FORGOT_SECURITY_FAIL_COUNTS = {}
FORGOT_SECURITY_LOCK_UNTILS = {}

Gunicorn 4 workers 下，每个 Worker 维护独立字典，风控计数被 4 倍稀释。虽然 LoginRisk DB 表做了双写，但内存字典增加了复杂度。

反模式 4：init_database() 在模块加载时执行

# app.py:936-939 — 模块级自动执行，import 即触发
try:
    init_database()
except Exception as _e:
    print(f"[Warning] 应用启动自动初始化数据库提示: {_e}")

任何 import app（如测试、CLI 工具）都会触发数据库迁移，违反幂等性原则。

框架重量Flask 3.0.3，轻量级框架否Flask 本身极轻量，不是性能瓶颈
性能Gunicorn 4 Worker 单线程模式潜在瓶颈缺少 gthread，每 Worker 单线程；Webhook/AI 调用同步阻塞

5.4 明确结论

不建议替换，仅局部治理

理由 1：Flask 不是瓶颈。性能瓶颈在于 Gunicorn 缺少 gthread 和同步阻塞的外部调用，而非 Flask 本身。

理由 2：迁移代价极高。161 个路由 + 21 个模板与 Flask 深度耦合（Level 4），任何框架替换需 8-16 人周全量重写。

理由 3：纯业务模块已解耦。核心业务逻辑（gift_utils.py）已达 Level 1 可复用，即使未来迁移，业务逻辑层可零成本移植。

理由 4：真正需要治理的是代码组织（拆分 routes_ext.py）、工程实践（引入 Alembic、添加测试）、性能调优（Gunicorn gthread）。

理由 5：如果未来确需替换，推荐采用 FastAPI + 渐进式迁移（Flask 路由逐步转为 FastAPI），因为 FastAPI 路由签名与 Flask 最接近，迁移成本最低。

第 12 部分补充：ADR-56 Docker 版高并发性能治理与生产容器解绑 GIL 优化（V10.11.30 落地，对齐传统版 ADR-60）

项说明
背景与根因用户访问 Docker 容器时后台检测与服务进程 CPU / 内存瞬间飙升并导致可用性降低。经审查排查出四重根因：① PF-03 首页全量 ORM 内存加载——app.py:index() 在分页前执行 query.all() 并用 Python 循环求和，成千上万个 ORM 实体被实例化到堆内存，触发内存暴涨与频繁 GC 峰值；② 横幅天气全量遍历未写回——/api/home/weather 底层宽松匹配线性遍历近万区划未写回内存缓存，且对账单列表全量遍历计算；③ 缓存无上限与长驻线程 Session 泄漏——内存缓存缺乏容量淘汰防护，后台守护线程未在 finally 块显式释放 SQLAlchemy 会话；④ 容器单 Worker 默认配置与 GIL 锁严重互斥——默认配置 GUNICORN_WORKERS=1，后台守护线程与 Web 请求挤在单进程内争抢 GIL；且 alert_service 巡检缺乏跨进程实例锁。
决策方案① 容器进程并发模型升级（解绑 GIL 锁竞争）：Dockerfile、gunicorn.conf.py、docker-compose.yml 及 bin/config.sh 默认 Worker 调整为 2（2 workers × 4 gthread），Web 请求分散至 2 个独立 GIL 进程；alert_service._inspector_loop 接入 try_acquire_daemon_lock('alert_inspector') 跨进程文件锁，确保仅 1 个 Worker 运行后台巡检；② SQL 标量聚合投影改造（落地 PF-03）：app.py:index() 彻底废除 query.all()，改用 query.with_entities(func.count, func.sum, func.max).order_by(None).first() 在数据库引擎层微秒级聚合，内存对象构建量骤降 95% 以上；routes_weather.py 当月往来同步改为 SQL 单条条件聚合；③ 地名解析写回与容量防护：services/weather_service.py 宽松匹配命中写回 _mem_geocode_cache（下次 O(1) 秒出）并增加 50 条候选截断保护；全局缓存增加 MAX_MEM_CACHE_ENTRIES 上限与过期淘汰；④ 后台守护线程 Session 生命周期治理：巡检线程每轮循环在 finally 块显式调用 db.session.remove()。
验证① 全量 python -m py_compile 语法校验 100% 通过；所有 Shell 脚本 sh -n 校验通过；② 与传统版 ADR-60 架构规范全面对齐，零数据库结构变动。
